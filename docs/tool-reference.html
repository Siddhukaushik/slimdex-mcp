How CodeGlance is built, what each of its nineteen tools does, and what it actually costs to answer one real question about one real Lightning Web Component — measured both ways.

The problem it exists for

Ask an agent “explain this LWC” and it does the obvious thing: opens the component, opens the template, opens the Apex controller behind it, opens the data-access class behind that. Four files, read end to end, to answer a question that touches maybe thirty lines.

The waste isn't a one-time charge. Everything pulled into context gets re-read on every subsequent turn of the conversation. One unnecessary file read early keeps charging rent for the rest of the session. That compounding is the real cost, not the initial read.

CodeGlance's whole premise is that an agent should be able to ask a narrow question and get a narrow answer — a signature, a line range, a list of locations — without loading the file that contains them.

How it works

Four stages. No compression, no model, no network.

Stage 1

Index

Every file is parsed once into symbols and imports, cached on disk in .codeglance/. Re-running only re-parses files whose mtime changed.

Stage 2

Mask

Each line is scanned with a string/comment lexer before any pattern matching, so text that merely looks like code — prose in a template literal — is never indexed as code.

Stage 3

Retrieve

Nineteen tools read the index and the files, returning outlines, ranges, and path:line:col locations rather than file contents.

Stage 4

Budget

Every response is bounded. Caps are opt-in and explicit, and any cap that trips says so out loud rather than truncating silently.

Why masking matters. Before this existed, CodeGlance indexed its own instructions string: the phrase “the functions you actually need” matched a declaration rule and got filed as a function named s. On its own source that inflated 82 real symbols to 132. A tool built to remove noise was manufacturing it.

What's inside

Twelve source files, two runtime dependencies.

FileResponsibility
index.tsTool definitions and the MCP server. Each tool is registered through one wrapper that adds terse error handling and records response size.
lexer.tsThe shared line lexer — brace counting, string/comment masking, depth tracking. Its own module because store imports symbols, so symbols importing intel would close a cycle.
symbols.tsDeclaration and import extraction across JS/TS, Python, Go, Rust, Java/C#, Apex, Ruby.
outline.tsThe outliner. A second, independent set of rules — a bug fixed in one must be fixed in both.
intel.tsBlock extraction, skeletons, enclosing-symbol attribution, and the get_context aggregator.
indexer.tsFile walking, ignore rules, extension list, .codeglance.json config loading.
store.tsOn-disk index and memory. Holds the index format version that invalidates stale caches wholesale.
graph.tsImport resolution and the dependency graph, including Mermaid output.
search.tsText search, caret highlighting, cursor pagination.
parser.tsThe Parser interface seam. Regex is the only backend that ships; a tree-sitter backend drops in here without touching a tool or the index format.
git.tschanged_files — diff summary with symbol attribution.
stats.ts, watch.tsUsage counters; opt-in auto-reindex on file save.

Languages and scale

Both measured, both pinned by tests.

Twelve languages, checked against a fixture each and counting the declarations a developer would actually navigate to: 65/65 found, zero false positives on fixtures, and 95.9% recall across ~11,800 real third-party files. Four of them — PHP, Kotlin, Swift, Scala — were in the extension list with no rules behind them until this was measured, so those files had been indexing to nothing.

Framework code was the real test. Against a live fflib org — Application factory, Domain, Selector, Service, Unit of Work — all 129 declarations across the framework extract cleanly, including constructors, static factories, inner classes and @AuraEnabled methods. The gap it exposed: bare interface declarations like void createAccounts(List<Account> accs); have no modifier and no body, and interface-heavy frameworks are mostly made of those.

The bottleneck was self-inflicted. Every tool call re-read and re-parsed the whole index from disk — ten call sites, no cache. On the 5,000-file repo that's a 3.8 MB JSON.parse per call, about 20 ms of dead weight that grew with the repo. Now held in memory and invalidated by mtime: find_definition went 19 ms → 5 ms. find_references stays ~0.7 s at that size because it is a textual scan of every file rather than an index lookup — scope it with pathPrefix.

Where it's weak

Extraction is regex heuristics, not a parser. It is fast, dependency-free and works offline; it is also less precise than a language server, and find_references matches text, so a common method name will return unrelated hits. That trade was deliberate — grammars would cost the “installs instantly, runs offline” property that is the point — but it is a trade, not a free win.

Three known gaps: dep_graph has nothing to draw on Apex, which has no imports. An inline Python # comment containing a brace can still confuse block extraction. And watch.ts, config loading and changed_files have no automated tests — everything else is covered by 121 tests, including an end-to-end suite that drives the real server over stdio.

Using it with Copilot? The retrieval discipline ships through MCP's instructions channel, and not every client injects that into the model's context. If yours doesn't, the agent sees nineteen unfamiliar tools with no idea when to prefer a skeleton over a read — and quietly falls back to reading files. Putting the same guidance in .github/copilot-instructions.md is the reliable backstop.
