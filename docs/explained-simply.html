CodeGlance · in plain words

How do you read a library without reading every book?

That is the entire problem CodeGlance solves. Everything below is that one idea, applied nineteen different ways.

First, the problem

When you ask an AI assistant a question about your code, it can't see your files the way you do. It has to be handed them. So when you ask something small — “what does this component do?” — it does the only thing it knows how to do: it opens the file and reads the whole thing. Then the next file. Then the next.

Imagine asking a librarian “which page mentions the refund policy?” and watching them read you four entire books, cover to cover, in case the answer is in there somewhere. You'd get your answer. It would just take forever and cost a fortune.

And here's the part that really hurts. The assistant has a limited memory, and everything it has read stays in that memory and gets re-read every single time you say something new. One unnecessary file early in a conversation doesn't cost you once. It keeps charging you, over and over, until the conversation ends.

The whole idea in one line. CodeGlance gives the assistant a way to ask for exactly what it needs — one page, one paragraph, one address — instead of the whole book.

The picture to hold in your head

Think of your codebase as a library, and CodeGlance as the front desk.

A good library doesn't make you read books to find things. It has a catalog that says which book each topic is in. Each book has a table of contents. Each page has a number, so you can be told “page 41” instead of being handed the book. And there's a librarian who, if you ask one good question, can answer it without you opening anything.

That's it. That's CodeGlance. The nineteen tools are just the nineteen different things you can ask at that desk.

How it's built, in four plain steps

No AI inside it. No internet. It's a filing system.

1

It reads everything once and writes a catalog

It goes through your files and notes down every function, class and method, and what page — sorry, what line — each one is on. That catalog gets saved to disk. Reading it back later is instant.

2

It only re-reads what actually changed

Next time, it checks the “last modified” date on each file. Untouched files are skipped entirely. Updating the catalog for a big project usually costs nothing, so it can be refreshed constantly.

3

It's careful about what counts as real

Text inside quotes and comments is blanked out before it looks for anything. Otherwise a sentence in a comment that happens to contain the word “function” gets filed as if it were real code — which is exactly the bug that used to make its own catalog 60% junk.

4

It refuses to hand over too much

Every answer has a size limit. If there were 68 results and you're getting 3, it tells you it's showing 3 of 68. It never quietly cuts things off, because an assistant that doesn't know it got a partial answer will confidently act on it.

How they work together

No tool does much alone. Here are three real jobs, start to finish.

“Explain this component to me.”

achLpDashboard · the LP dashboard

  1. outline_file — see the component's 14 parts and their line numbers. Now you know it wires two things and computes several totals.
  2. dep_graph — see what it pulls in: two Apex methods from the portal controller.
  3. get_file_skeleton — look at that controller's shape without reading it. Six methods, one of them the one you care about.
  4. get_context — ask about that one method: where it's defined, what it returns, who calls it.
  5. read_lines 14–46 — finally read actual code: only the two wired handlers.
Same understanding either way. Reading the four files outright: 20,708 characters. Asking precisely: 2,709. About 7.6× less — and every line the assistant reasons about is still in front of it.

“I want to change this method. What breaks?”

the classic scary question

  1. find_definition — confirm which one you mean. If two things share the name, you find out now rather than after the change.
  2. find_references — every place it's used, and the function each use sits inside. On your org this is what catches an LWC quietly depending on an Apex method.
  3. dep_graph — which files lean on the file you're editing, so you know how far the ripples go.
  4. get_symbol_context — read the method itself, and nothing around it.
  5. memory_save — write down what you learned about why it's built that way, so nobody re-derives it next month.
You get a blast radius before touching anything, without loading a single whole file.

“I haven't touched this project in three weeks.”

coming back cold

  1. index_repo — refresh the catalog. Only files you changed get re-read.
  2. changed_files — what's half-finished, and which functions the unfinished edits sit in.
  3. memory_search — the notes past-you left about decisions and traps.
  4. repo_map — re-orient on the overall shape.
  5. batch — bundle the next few lookups into one request.
You're caught up in a handful of small answers instead of re-reading your own project.

What it actually saves

Two numbers, and they look like they disagree. They don't — they're measuring different things.

one question
20,708 characters — read the files
same question
2,709

On a single question, the saving is large — roughly 8×. Across a whole working session it's much smaller, around 29%. That's not a contradiction, and it's worth understanding.

Most of what an assistant carries around isn't your files. It's fixed overhead — its instructions, its list of available tools, your project's setup notes. CodeGlance doesn't touch any of that. It only trims the file-reading part. So the slice it improves gets dramatically cheaper, while the total bill improves modestly.

Take both with salt. These came from one project, measured once, by the person who built the thing. They're a real measurement, not a guess — but they're not a benchmark, and your mileage depends on whether your assistant actually reaches for these tools instead of falling back to reading files.

Where it's honestly weak

It recognises code by pattern-matching, not by truly understanding the language. That's why it installs in a second and works offline with no setup — and also why it's less precise than the heavyweight tools built into an IDE. Two real consequences:

“Who uses this?” is answered by matching text. If two unrelated things share a name, both show up. It's a strong lead, not proof.

The relationship diagram no longer needs import statements. Some languages never import each other the way JavaScript files do, so their map used to come back empty; today the catalog notices when one file's code mentions another file's class by name (ignoring comments and quoted text) and draws that as a connection — “which class implements this interface” and “which trigger uses this handler” both fall out of it. It also reads the configuration files in your project: a settings record that names a class becomes a connection too, so “what wires this up” gets an answer. The only thing it can't draw is a setting that lives purely in a running system and was never saved into the project.

And one thing it will never do: send your code anywhere. There is not a single network call in it. It reads files on your machine and writes its catalog next to them. That's the whole of its behaviour.
